# NetProxy 9.0 跨平台与 Android 双模式总体规划

> 版本：v0.3（架构决策讨论稿）  
> 日期：2026-10-10  
> 适用范围：Android Root、Android 无 Root VPN、Windows、Linux；统一 Go Core、内置 WebUI、Tauri 2 可选原生外壳  
> 状态：仅规划，尚未执行代码修改或跨平台实机验证

## 0. 一页结论

NetProxy 9.0 采用 **Go Core First + Embedded WebUI + Optional Tauri Shell + Platform Adapters** 架构：

1. **共享一套 Go 业务源码**：Catalog、Provider、订阅、节点、配置事务、服务状态、管理 API 等只实现一次。
2. **共享一套 WebUI**：React + TypeScript + shadcn/ui，构建产物由 Go `embed` 内置，普通浏览器和 Tauri 均使用同一份 UI。
3. **Tauri 2 只是可选原生外壳**：Android/Windows/Linux 统一窗口与前端，使用最小权限原生插件提供系统特有能力，不复制代理业务。
4. **Android 保留 Root 模式**：Root 模块独立运行 Go CLI/后台与 sing-box，继续支持 eBPF、Root TUN、热点等现有特性。
5. **Android 新增无 Root VPN 模式**：APK 内集成由共享 Go 源码构建的原生库及 sing-box/libbox，由 Kotlin `VpnService` 创建 TUN、保护 socket、管理 Android 服务生命周期。
6. **Windows/Linux 独立后台**：Go Core 与 sing-box 独立运行；Tauri 可退出而不中断代理；浏览器可直接访问本机 WebUI。
7. **默认不开放远程控制**；高权限管理 API 需要独立鉴权和会话控制，不能将“仅监听 localhost”作为认证方式。

**关键限制**：“共享 Go Core”是共享源码和领域逻辑，**不是**四种运行模式必须使用同一份可执行文件。Android 无 Root VPN 的 Go 组件预期编译进 `.so` / AAR，不能直接沿用目前以 `exec.Command` 启动 sing-box 的 Root 服务生命周期。

## 1. 产品矩阵与明确边界

| 发行形态 | Go Core 运行方式 | UI 入口 | 代理数据面 | 安装要求 |
| --- | --- | --- | --- | --- |
| Android Root | Root 模块独立 Go 二进制 | 浏览器 / Tauri APK | sing-box eBPF / Root TUN | Magisk / KernelSU / APatch 等 Root 环境 |
| Android VPN | APK 内 Go 原生库，由 Android Service 宿主管理 | Tauri APK；Core 服务在线时可使用浏览器 | `VpnService` TUN + sing-box/libbox | 无 Root；用户显式授权 VPN |
| Windows | 独立 Go 后台 + sing-box | 浏览器 / Tauri 客户端 | 先 mixed，再 TUN/系统接管 | Windows 服务、驱动及权限按功能配置 |
| Linux | 独立 Go 后台 + sing-box | 浏览器 / Tauri 客户端 | 先 mixed，再 TUN/系统接管 | systemd 与路由权限按功能配置 |

- **核心管理功能保持一致**：服务状态、节点、订阅、Provider、日志、配置、模式、规则。
- **系统能力按平台声明**：Android Root eBPF 不会在无 Root VPN 中出现；Android VPN 按应用分流须使用 `VpnService.Builder` 提供的平台机制，并不等于可以复用 Root UID 规则；Windows/Linux 的进程识别和网络接管需要独立适配。
- **VPN 并不意味着可同时占用其他 Android VPN**：一般受单活跃 VPN 限制。
- **Android 无 Root 下浏览器能否访问 WebUI**取决于 APK 所属 Go 控制服务是否在线，不能保证在 APK 被强行停止、VPN 未启动且系统未允许后台启动时仍可访问。
- **Tauri 不负责实际代理或保活**，也不负责独立持久化第二套业务配置。

## 3. 服务边界与通信设计

### 3.1 Go Core（唯一通用业务事实源）

- 管理节点与订阅的事务、冲突和回滚；保持现有 Catalog / Provider 事实源。
- 管理 sing-box 配置投影、运行时状态和日志，维持 `schema=1` 错误码及 CLI 语义的一致性。
- 使用 `embed.FS` 提供前端资源；提供带鉴权的 HTTP API 和事件流。
- 将平台依赖降到必要接口：服务进程、TUN、UID/应用、路径、设备网络、权限等。
- `netproxyctl` 继续保留 CLI 模式，不强迫终端用户安装 Tauri。

### 3.2 管理 API

拟定接口（**示意，不是当前 8.x 已存在的 API**）：

```text
GET  /api/v1/health
GET  /api/v1/capabilities
GET  /api/v1/service/status
POST /api/v1/service/start
POST /api/v1/service/stop
GET  /api/v1/catalog
POST /api/v1/subscriptions/update
GET  /api/v1/config/{section}
PUT  /api/v1/config/{section}     // revision / optimistic concurrency
GET  /api/v1/events              // SSE，失败可重连
```

- 统一结果 envelope，延用机器接口 `schema=1`，但 API 独立标注 `api_version`、`core_version` 与能力清单。
- CLI 与 HTTP API 调用同一 Go Application Service，不允许 HTTP handler 再拼接 shell 命令调用自身 CLI。
- 写操作需要严格权限、校验、并发事务、冲突响应和必要的幂等语义。
- 推荐 SSE 用于状态/流量/事件推送；大量高频双向控制再评估 WebSocket。

### 3.3 Tauri 与 WebUI 的连接

正常流程：应用启动 → 检测 Core → 启动/连接本机 Core（根据平台和权限）→ 校验版本/会话 → WebView 加载 Go 内置 WebUI → 按能力声明显示原生增强功能。

因为 WebUI 来自 Go 的 loopback HTTP origin，**不能假设它会自动拥有 Tauri 插件权限**。Tauri 的远程来源 capability 能赋权，但应限制到固定受信任来源与极小的命令集合，特别注意 Android/Linux 的 iframe 来源边界。

建议在 PoC 中比较：

- A. WebView 直接加载 `http://127.0.0.1:<port>/` + 严格限定远程 capability；
- B. 一个 Tauri 打包的可信 bootstrap origin，经受控转发访问 Go WebUI；只暴露验证过的 Native Bridge。

选择标准是：**不重复打包业务前端、不授予任意 shell 或文件系统权限、不影响浏览器访问**。配置具体端口、Origin 与身份校验方式，须经过 Android/Windows/Linux 实机验证，不能纸上定案。

### 3.4 Native Bridge（可选能力）

```ts
interface PlatformCapabilities {
  nativeAvailable: boolean;
  appPicker: boolean;
  notifications: boolean;
  tray: boolean;
  quickSettingsTile: boolean;
  fileDialog: boolean;
  deepLinks: boolean;
  vpnService: boolean;
}
```

前端使用 capability 驱动的渐进增强，不在业务页面散落操作系统判断。Tauri 仅允许“列出应用”“选择文件”“发送通知”“引导 VPN 授权”等窄口径操作。浏览器访问时缺少 Native Bridge 不妨碍核心管理功能。

## 4. Android 双模式——核心设计决策

### 4.1 Root 模式：保留成熟路径

```text
Tauri / Browser
       ↓ API
Root Module / Go Core（独立服务）
       ↓
sing-box 独立进程（eBPF 或 Root TUN）
```

- 保留 Magisk/KernelSU/APatch 模块形态、Root 能力与 CLI。
- 独立 Go Core 内置 WebUI 和 HTTP 管理接口，必须限制网络绑定与高权限 API。
- Root 模式与无 Root VPN 模式不应同时接管本机流量。
- 原有 Root 分应用多用户语义 `<user-id>:<package>` 与 eBPF 策略保持不变。

### 4.2 VPN 模式：共享 Go 源码，新的运行载体

```text
Tauri APK
  ├─ Android MainActivity / WebView
  ├─ Kotlin Native Plugin
  ├─ NetProxyVpnService（由 Android 管理生命周期）
  │    ├─ VpnService.prepare() / Builder.establish()
  │    ├─ TUN FD + protect(socket) + network callbacks
  │    └─ Go library bridge (.so / AAR)
  │          ├─ NetProxy 共享业务组件
  │          ├─ HTTP API + Go embed WebUI
  │          └─ sing-box / libbox TUN runtime
  └─ 受控 App 私有配置目录
```

- 最适合验证的是 `gomobile bind` 生成 AAR/Go JNI 接口；也可评估 `-buildmode=c-shared` + 自建 JNI。二者只选一条主路线。
- Android 不通过可写目录中解压并执行独立二进制来运行 VPN 核心；优先使用被 APK 正常打包的 native library。
- 只实例化所需的 Go runtime，避免引入多个独立 Go 运行时或复制一份 sing-box 代理引擎。
- Kotlin `VpnService` 负责 TUN FD 生命周期、路由、DNS、应用允许/排除列表、网络保护、系统撤销与前台服务通知。
- libbox 通过平台接口 `OpenTun()` / `AutoDetectInterfaceControl()` 等接入平台提供的 TUN FD 和出站控制。
- Android `VpnService.protect(fd)` 保护 sing-box 出站 socket，防止循环进入自身 TUN。
- 关闭窗口不应停止 VPN；系统撤销、权限回收、被系统终止等情况必须触发正确状态与资源清理。
- Android 14+ 需要核对实际 targetSdk 对应的前台服务类型声明、通知和系统限制。

### 4.3 为什么不能原封不动搬入现有二进制

现有仓库：

- `internal/inbound/tun.go` 强制 `auto_route=true` 和 `auto_redirect=true`；Android 系统 VpnService TUN 需要独立配置投影，不能强制复用 Root/Linux auto_redirect。
- `internal/module/lifecycle.go` 使用 `exec.Command(sing-box run ...)` 启动外部进程；VPN 运行载体需要改为集成式 libbox 服务实现。
- `internal/paths/paths.go` 默认 `/dev/netproxy` 与模块路径；无 Root 模式应使用 Android App 私有目录。
- `internal/inbound/applications.go` 的 Android 包管理命令以及 UID 规则，不能直接代替 `VpnService.Builder` 的应用过滤。

**策略：只改平台边界和运行时适配，不改节点/订阅/Catalog 的领域业务语义。** 原 Root 路径必须通过回归测试保证兼容。

### 4.4 状态机与互斥

建议明确两个维度：

- `runtime_mode`: `root | vpn`（Android 运行载体选择；根本不同于入站后端）。
- `inbound_backend`: `ebpf | tun | ...`（平台内实际入站选择）。

不要把 `vpn` 混进原 `backend=ebpf|tun` 枚举中；那会将系统授权模型和流量接管方式混为一谈。

状态转换原则：用户确认 → 停止旧运行载体并验证流量接管释放 → 初始化新载体 → 校验配置及权限 → 启动 → 回读真实状态。失败需要显示当前真实状态，不静默回退。推荐初版仅在明确停止旧模式后允许切换，而非无缝切换。

### 4.5 配置与迁移

- Root 模块数据目录与 APK 私有数据目录天然隔离；共享 **schema**，不直接跨安全域读写对方文件。
- 设计显式“导出/导入配置与节点”流程，敏感字段加密或由用户确认；避免 Root/API 密钥被导入普通 App 明文目录。
- 分应用名单分别处理：Root `<user-id>:<package>` 不能无损转换为 VPN 应用列表；迁移时报告被跳过的分身/用户规则。
- VPN 应用选择列表使用 Android 平台返回的包名和系统允许/排除名单机制；路线切换时可能要重建 VPN 接口。

## 5. Windows / Linux 运行模型

### Windows

- Go Core 作为后台服务或受控用户级服务进程，与 Tauri GUI 分离。
- sing-box 作为被管理的实际代理核心；Windows 进程健康检查、停止/重载、日志及路径必须做 Windows 实现。
- 首个里程碑优先 **mixed HTTP/SOCKS5 入站**，后续再支持 TUN、系统路由/驱动及管理员权限。
- Tauri 原生能力：托盘、单实例、通知、开机启动引导、系统代理、原生文件选择器。
- 服务端权限与当前用户数据要明确边界；有高权限服务时，使用受控身份验证/本机 IPC，不应把所有 API 暴露给任意用户进程。

### Linux

- Go Core 支持 systemd，CLI 和浏览器 WebUI 可在无图形环境独立运行。
- GUI 是附加安装项，不必让服务器安装 Tauri/GTK/WebKit。
- 先 mixed，再 TUN；TUN 权限可能依赖 `CAP_NET_ADMIN`、路由规则、系统配置。
- Tauri 提供托盘、桌面通知、文件对话框、窗口及桌面集成。

## 6. 安全基线（不允许推迟到发布前）

1. **默认只监听 loopback**；LAN/远程访问是独立可选功能，不在 9.0 初版默认开启。
2. **所有管理操作必须鉴权**：尤其 Android Root 模式中 Go Core 可能以 Root 权限运行；同机其他 App 也可能尝试连接 localhost。
3. **浏览器会话与 API 认证分离**：一次性配对或本机受控会话；Cookie 与 CSRF 防护、Origin/Host 校验、CSP、防 DNS rebinding 和 XSS。
4. **严禁任意 Shell Bridge**：WebUI 不得取得 `su -c`、任意文件读写或任意命令执行能力；Root 权限永远由 Go 的受限业务入口管理。
5. **Tauri 原生能力最小授权**：只允许已验证的本地页面使用指定操作，禁止泛化 `shell:execute`。
6. **服务与界面分离**：禁用或退出 Tauri 不应悄悄修改 Core 自启或代理状态。
7. **敏感数据**：节点凭据、订阅 URL、访问令牌、诊断日志脱敏；权限文件和 Android 私有数据采用最小授权；不在 URL 查询参数里传长期访问密钥。
8. **本地端口被占用 / 假冒服务**：客户端不能只依据端口联通认为 Core 可信；需对版本、实例身份和安全握手做验证。
9. **远程 WebUI** 后续再支持明确配对、TLS、设备权限撤销及审计，不能靠“改成 0.0.0.0”直接开放。

## 8. 实施阶段与验收门槛

### P0｜技术可行性验证（阻塞后续开发）

- **Android VPN**：Kotlin VpnService 成功拿到 TUN FD；reF1nd libbox 构建为 APK 可加载的 AAR/.so；真实 TCP/UDP/DNS 流量能够出站；socket protect 正确；退出 Tauri 窗口不断流。
- **Tauri 外壳**：同一个 Go WebUI 在 Android、Windows、Linux 真实设备可打开；原生桥只赋予受限能力；普通浏览器同样可管理；未启动 Core 时能展示可信的连接错误页。
- **平台差异**：编译 Android Root CLI、Linux amd64/arm64、Windows amd64 的实际依赖；验证同一套业务源码可以在 VPN 原生库内构建，识别 `go.mod` Android-only/CGO 依赖。
- **停止门槛**：上述任一关键目标不可实现时先收敛替代方案，不开展大规模 UI 重写。

### P1｜Go Core HTTP API 与内置 WebUI

- 从现有 CLI handler 下面抽取/复用 Application Service，新增受保护 API；状态查询、节点/订阅、服务控制完整可用。
- React 构建资源通过 `embed.FS` 内置，浏览器能独立操作；本地会话鉴权、错误契约和事件推送通过测试。
- 验收：断开 Tauri 后浏览器管理功能不退化；没有第二份业务状态；Root 旧 CLI 不回归。

### P2｜统一 React UI 与 Tauri 薄外壳

- 实现响应式仪表盘、节点、订阅、入站、配置、日志、设置；中/英/俄三语行为与现有 Android 版本对齐。
- Tauri Android/Windows/Linux 共享界面；Native Bridge 以 capability 渐进增强。
- 验收：三端与浏览器通过同一套管理用例测试，浏览器缺少原生功能时不影响核心控制。

### P3｜Android Root 客户端迁移

- Kotlin Tauri Plugin 实现 Root 检测、应用选择、快捷磁贴、文件共享/导入、系统通知。
- APK 尽量保持旧 `applicationId=com.fanjv.netproxy`、兼容签名和 versionCode 升级链。
- 验收：老用户覆盖升级、Root 授权、应用分身、配置 revision、模块更新、诊断导出均正确。

### P4｜Windows / Linux 独立 Core

- 平台服务、路径、PID/进程管理、配置、日志、打包/卸载；先 mixed 入站，后 TUN。
- Windows 托盘和系统集成；Linux systemd 和无 GUI 流程。
- 验收：关闭 Tauri 不中断代理、独立 CLI 可管理、重启后服务状态正确、无 GUI Linux 可完整管理。

### P5｜Android VPN MVP

- SDK 形式集成共享 Go Core 与 libbox；实现 `VpnService` + FD + protect + DNS/IPv4 TCP/UDP。
- 节点、订阅、模式和运行状态共享语义；App 私有数据目录；与 Root 路径互斥。
- 验收：非 Root 真机可安装、授权、连通、切换节点，前后台正常；Android VPN 撤销时无资源泄漏。

### P6｜双模式完善与平台增强

- Root ↔ VPN 显式切换与数据迁移；按应用过滤、IPv6、热点/多用户边界提示、网络切换、Always-on VPN 验证。
- Windows/Linux TUN 与系统代理、自启/托盘；异常恢复、遥测、日志脱敏。
- 验收：断网、飞行模式、Wi-Fi→蜂窝、VPN 权限撤销、后台回收、核心异常退出均有可解释状态。

### P7｜发布与稳定性验证

- Android Root 模块 + Tauri APK；Windows 安装包与 Core 服务；Linux Core 包与可选 GUI 包。
- CI 加 Go 单测、Android SDK 构建、Tauri 三端构建、API 契约与 Windows/Linux 进程模拟；VPN/eBPF/多用户须真实设备回归。
- 验收：签名更新、版本矩阵、故障恢复、回滚路径、安全清单、许可证与第三方 NOTICE 完整。

**发布策略**：不要强求 P0–P7 全部完成后才有可用版本。先发行可验证的 9.0 Alpha（Go WebUI + Root 客户端），随后扩展桌面、Android VPN；正式稳定版涵盖哪些平台以达到验收标准为准，不凭日期硬性承诺。

## 9. 主要风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| reF1nd libbox 当前版本无法生成可用 Android AAR | VPN 模式受阻 | P0 优先实际编译与真机验证；评估固定版本、接口适配或独立内部 bridge |
| Tauri 外部 localhost origin 的插件权限与 iframe 安全问题 | Native Bridge 不安全或不可用 | 先做 A/B PoC；最小 capability；必要时使用可信 bootstrap 和受控转发 |
| Android 被系统杀死或用户强停 | VPN/Core 服务不可达 | `VpnService` 正确前台化、状态恢复；明确系统行为限制，不承诺强停后仍在线 |
| Root 模式与 VPN 模式同时接管 | 丢包、DNS 故障、路由冲突 | 显式互斥、状态验证、失败不自动混合启动 |
| Go 原生库体积和启动性能 | APK 膨胀、首启变慢 | 单一 Go runtime、ARM64 优先、性能与内存真机测量 |
| Android 8.x 旧版 APK 升级失败 | 老用户数据丢失 | 固定包名/签名/versionCode；先小范围覆盖安装验证 |
| Windows/Linux 服务模型与权限差异 | 无法停止、重载或自启 | 平台独立适配、真实 OS CI/集成测试，先 mixed 后 TUN |
| 把 Go API 暴露在 localhost 就当作安全 | Root 权限可被滥用 | 始终鉴权+CSRF+Origin/Host 检查、浏览器配对、接口最小授权 |
| 9.0 一次性改造范围过大 | 影响 8.x 稳定性 | 以独立分支/里程碑渐进迁移、每阶段明确 Go/No-Go 条件 |

## 10. 关键工程决策（建议定稿）

| 决策 | 建议 |
| --- | --- |
| 主业务语言 | Go，绝不为 Tauri 重写业务到 Rust/Kotlin |
| 主前端 | React + TypeScript + Vite + shadcn/ui + Tailwind |
| Go WebUI | `embed.FS` 内置；只维护一份业务前端 |
| 原生客户端 | Tauri 2，Android/Windows/Linux 同一项目 |
| Android Root | 沿用 Root 模块与独立 Go CLI、sing-box 子进程 |
| Android 无 Root VPN | Kotlin VpnService + Go native library + libbox |
| Android 双模式 | 一个 APK，两个互斥的运行载体，数据显式迁移 |
| Windows/Linux | Go 独立后台，Tauri 可选；先 mixed 再 TUN |
| 浏览器管理 | 保留完整业务能力；原生操作渐进增强 |
| API | Go Application Service 统一抽象，HTTP/CLI 共用；新接口要鉴权 |
| 移植顺序 | P0 风险验证 → API/WebUI → Tauri/Root → 桌面 → VPN 完善 |
| 现有 8.x | 稳定维护，不直接在生产主线大爆炸式替换 |

## 11. 建议第一批实际改动（P0 专用）
