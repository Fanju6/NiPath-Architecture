# NetProxy 9.0 跨平台架构与实施规划

> 文档版本：v0.2（架构讨论稿）  
> 编写日期：2026-10-10  
> 项目仓库：https://github.com/Fanju6/NetProxy-Magisk  
> 适用范围：Android（Magisk / KernelSU / APatch）、Windows、Linux  
> 状态：设计建议，**未开始代码修改，未完成三端兼容性验证**

---

## 0. 一页决策摘要

### 已确定的产品路线

1. **Go Core First**：Go 管理核心是独立、完整、可无图形界面运行的程序，管理 NetProxy 的节点、订阅、配置、服务生命周期和后台任务。
2. **Embedded WebUI**：React + TypeScript 构建出的静态 WebUI 资源编译内置于 Go Core；Go 提供 HTTP API 与静态界面；不维护第二套业务 UI。
3. **Optional Native Shell**：Android、Windows、Linux 统一采用 Tauri 2 制作图形化软件包；Tauri 负责 WebView、托盘、文件选择、通知、权限请求等系统集成，**不是服务运行的前提**。
4. **Native Capabilities**：各平台特殊功能留在 Kotlin / Rust（或调用操作系统 API）的平台插件中；业务事实源仍由 Go 持有。
5. **Independent Proxy Engine**：`sing-box` 独立于 Go Core 运行，不因为 Tauri 被关闭而退出。当前 reF1nd 分支的 Service API 必须保持兼容。
6. **单仓库、单套业务 UI、多平台发行**：Go 后端、React WebUI、Tauri 应用和 Android Root 模块在同一仓库协同开发。

### 明确不做

- 不为 Android/Windows/Linux 各自开发一套业务页面。
- 不将全部 Android 平台逻辑改写为 Rust。
- 不让 Tauri 直接承担节点、订阅、Provider、核心运行状态等业务事实源。
- 不为了桌面化而把 sing-box 与 `netproxyctl` 强行合并为一个进程。
- 不把 KernelSU WebUI 作为正式架构的独立前端；Go 已经托管同一套 WebUI，必要时可以直接用浏览器访问。
- 不向 WebUI 暴露任意 Shell 命令执行接口。

## 1. 最终架构

```text
                       ┌────────────────────────────┐
                       │  React / TypeScript WebUI  │
                       │  唯一共享的业务图形界面    │
                       └─────────────┬──────────────┘
                                     │ 构建静态资源
                                     ▼
                  ┌───────────────────────────────────────┐
                  │               Go Core                 │
                  │                                       │
                  │  embed WebUI  ── HTTP API / Events   │
                  │  Catalog · Provider · Subscription    │
                  │  Config · Lifecycle · Worker          │
                  │                                       │
                  │  CLI + 无界面服务 + 本地 Web 服务      │
                  └──────────────┬────────────────────────┘
                                 │ 管理、生成配置、Service API
                                 ▼
                        ┌────────────────┐
                        │ sing-box       │
                        │ 独立代理进程   │
                        └────────────────┘

用户访问方式（同一份 WebUI）：

  [Tauri Android APK]  ─┐
  [Tauri Windows EXE]  ─┼─→ Go 的 loopback HTTP → 内置 WebUI
  [Tauri Linux App]   ─┤      │
  [普通本地浏览器]    ─┘      └→ 管理 API

Tauri 为可信客户端额外提供原生能力：
  Android: Kotlin 插件 → PackageManager / Root 状态 / QS Tile / 通知 / 文件选择
  Windows: Rust 插件   → 托盘 / 通知 / 启动项 / 权限 / 文件选择
  Linux:   Rust 插件   → 通知 / 文件选择 / systemd 集成 / 桌面能力
```

### 1.1 独立生命周期

| 组件 | 启动/退出规则 | 职责边界 |
| --- | --- | --- |
| Go Core | 可在开机时独立启动、后台长期运行 | 控制面事实源、内置 WebUI、任务调度 |
| sing-box | Go Core 管理生命周期；独立进程 | 流量转发、TUN/eBPF 与规则执行 |
| Tauri App | 用户需要时打开或关闭 | 窗口、系统 UI、平台交互 |
| 浏览器 | 用户需要时打开或关闭 | 访问 Go 提供的 WebUI |

关闭 Tauri ≠ 停止 Go Core ≠ 停止 sing-box。

### 1.2 推荐 UI 技术栈

| 层 | 推荐 |
| --- | --- |
| 页面 | React + TypeScript + Vite |
| 组件体系 | Tailwind CSS + shadcn/ui + Radix UI |
| 状态 | TanStack Query（服务端状态）+ Zustand（少量本地交互状态） |
| 路由 | React Router |
| 图表 | Apache ECharts（必要时按需加载） |
| 图标 | Lucide |
| 本地窗口 | Tauri 2 |
| 共享后端 | Go（沿用 netproxyctl 业务包） |
| Android 原生 | Kotlin，保留必要的 libsu / 系统接口 |
| Windows/Linux 原生 | Rust 与系统 API，优先使用成熟 Tauri 官方插件 |

避免一开始堆叠大量前端依赖；移动端 WebView 的启动速度、内存占用和低端设备渲染需单独验收。

## 2. 结合当前仓库的现状评估

以下是依据 2026-10-10 对主分支源文件的检查形成的判断，不等于已通过实际跨平台测试。

### 2.1 可沿用的 Go 业务能力

当前路径为 `src/native/netproxy/`。建议继续复用：

- `internal/catalog`：Catalog、节点目录及持久状态；
- `internal/provider`、`internal/convert`、`internal/sharelink`：Provider、协议转换、分享与导出；
- `internal/subscription`、`internal/fetch`：订阅拉取和更新；
- `internal/config`：类型化配置和保存；
- `internal/serviceapi`：与 reF1nd sing-box 的控制面通信；
- `internal/logfile`、`internal/processlock`：日志与互斥锁的通用部分；
- `cmd/netproxyctl`：当前公开 CLI 与 `schema=1` JSON 输出契约。

### 2.2 实际存在的平台耦合

- `internal/paths/paths.go` 使用 `/dev/netproxy`，默认路径指向模块安装布局；
- `src/module/config/singbox/config.json` 存在 `/data/adb/modules/netproxy/...` 绝对路径；
- `internal/module/cgroup.go` 无条件处理 Linux cgroup 根组路径；
- `internal/module/lifecycle.go` 开机逻辑依赖 Android `resetprop`；
- `internal/module/service_process_windows.go` 的 `serviceProcessAlive` 当前是恒 `false` 占位；
- `internal/service/control.go` 的进程扫描及 CPU 统计依赖 `/proc`；
- `internal/worker/process_windows.go` 的 Worker 检测与终止逻辑存在占位；
- `internal/worker/network_route_unix.go` 使用面向 Android policy routing 的出口发现；
- `internal/inbound/applications.go` 使用 Android `cmd package` 解析应用 UID；
- `internal/inbound/tun.go` 强制 `auto_route` 和 `auto_redirect`，需区分 Windows/Linux；
- `src/webui/src/exec.ts` 当前依赖 `kernelsu.exec` 与固定模块路径，无法直接用作三端的普通浏览器管理界面。

### 2.3 现有 Android 原生资产不要直接删除

目前 `src/android/` 是完整 Kotlin + Compose + Miuix 管理器，具有 Root 交互、快捷设置磁贴、应用列表、配置编辑和诊断分享等能力。

迁移策略：**保留现有工程作为兼容与功能行为参考；逐步把平台能力提取为 Tauri Kotlin Plugin；新 React WebUI 验收完成后才替换 Compose 页面。**

## 3. 单二进制 WebUI 设计

### 3.1 目标

Go Core 的编译产物直接包含前端静态文件，无须部署独立 Node.js、nginx 或第二个 Web 服务。

```text
npm run build
  └── dist/ (HTML / JS / CSS / assets)
           ↓ 拷贝进入 Go 包下的嵌入目录
Go //go:embed
           ↓
netproxyctl (CLI + HTTP API + 内置 WebUI)
```

建议新增 `internal/webserver` 与 `internal/uiassets`，`uiassets` 负责 `embed.FS`，`webserver` 负责路由、鉴权、静态内容、缓存策略和服务版本接口。前端产物应通过构建脚本生成在 Go 包可嵌入的位置，避免 `go:embed` 跨越包目录限制。

**保持 `netproxyctl` 单 Go 可执行文件的原则**：可把 `serve` 作为公开受控命令，或者扩展现有 `__internal` 的后台服务入口，具体应与现有 `AGENTS.md` 的命令契约统一调整，避免产生两套命令调度器。

### 3.2 推荐端点（提案，不是现有接口）

```text
GET    /                       # 内置 WebUI
GET    /assets/...             # 嵌入式静态资源
GET    /healthz                # 最小健康状态；不含敏感信息
GET    /api/v1/meta            # Core 版本、API 版本、平台能力
GET    /api/v1/service         # 服务运行状态
POST   /api/v1/service/start
POST   /api/v1/service/stop
GET    /api/v1/catalog
GET    /api/v1/subscriptions
GET    /api/v1/config/...
GET    /api/v1/events          # SSE 或 WebSocket 状态流
```

不要为了 HTTP API 重写 Go 业务：HTTP handler 调用现有 domain/application 函数，CLI 继续调用同一份业务函数。不得通过 HTTP handler `exec` 另一个 `netproxyctl` 来转发业务。

### 3.3 版本与兼容性

- `core_version`：Go 核心版本；
- `api_version`：HTTP 管理协议版本，与现有 CLI 的 `schema=1` 区分；
- `ui_build`：内置 React 构建标识；
- `shell_version`：Tauri 客户端版本；
- `features`：Core 已实现的能力清单；
- `native_capabilities`：Tauri 外壳本机可提供的能力。

UI 的发布应跟随 Go Core，Tauri APK/EXE 可以在不涉及新增原生能力时独立更新。新增原生调用需做好功能探测及兼容降级。

## 4. Tauri 的正确职责与两条通信通道

### 通道 A：通用业务

```text
React → Go localhost HTTP API → 原有 Go 业务包 → sing-box
```

用于节点、订阅、分流、入站配置、服务状态、日志与升级检查等通用功能。

### 通道 B：平台专属 UI

```text
React → Tauri Command/Plugin → Android Kotlin / Windows-Linux Rust
```

用于应用列表与图标、Root 授权交互、系统通知、原生分享、文件选择器、快捷磁贴、桌面托盘等。

平台插件不直接修改 Catalog、Provider 或 sing-box 配置。原生文件选择返回受控文件句柄或暂存文件元数据，由 Go 的导入接口校验、保存。权限验证必须在插件实现侧进行，不能只由 UI 按钮的显示状态决定。

### 4.1 需要优先做的技术验证

Tauri 的主 WebView 加载 `http://127.0.0.1:<固定端口>/`，与 Tauri 打包的普通本地 HTML 不同。Tauri Capability 的 `remote.urls` 支持按远程来源限制 IPC 权限，但官方明确警示远程来源获得系统权限的风险。

应在 Android、Windows、Linux 上先验证：

1. Tauri WebView 能打开 Go Core 监听的 loopback URL；
2. Go 页面可以访问同源 HTTP API；
3. 页面可以调用**最小权限的自定义原生插件**；
4. 页面被重定向、发生 XSS、服务端口被其他进程占用时，不会获得危险原生能力；
5. Go Core 尚未运行时，Tauri 显示内置的最小连接/诊断页；
6. 核心版本不兼容时，Tauri 安全展示兼容错误，而不触发配置修改。

**重大架构关口**：如果远程 Go 页面直接调用 Tauri 插件的信任边界无法可靠满足，应让 Tauri 的最小可信本地页面承担受控原生调用和会话建立；不要为了“外壳轻薄”放宽系统权限。此情况下业务 UI 仍然只保留 Go 内置的一份，不构建第二套业务页面。

## 5. 管理 API、WebView 与 Root 的安全模型

这是 9.0 的阻断级要求，尤其 Android Go Core 以 Root 身份运行。

1. HTTP 服务仅监听 loopback（例如 `127.0.0.1`），默认**不对局域网开放**；IPv6 如启用需独立监听 `::1`，不能意外监听全部网卡。
2. **不能依赖 `localhost`、固定端口或 CORS 作为鉴权**。本机其他 App/进程也可能访问 loopback。
3. 管理操作必须采用实际的身份验证（短时会话、设备绑定或安全的客户端配对流程），高权限操作应有额外授权判断。
4. 浏览器访问应有独立登录/配对入口，不自动享有 Tauri 的原生插件权限。
5. 禁止将长期有效的 Root 管理 Token 放在 URL、前端构建产物、日志或公开配置中。
6. 对修改类 API 进行 Origin/CSRF 防护、请求体长度限制、幂等/并发控制和接口审计；事件流也必须授权。
7. Tauri 只能为经过验证的 Go Core 页面授予严格受限的远程 Capability；确认页面身份与进程/端口所有者，限制跳转和外链，防止端口劫持。
8. 不提供 `runShell(command)` 这样的通用高权限插件；只开放 `listApps`、`pickFile`、`requestRootAccess` 等必要、受校验的操作。
9. Go Core 与 Tauri 之间建立显式协议版本与功能清单。核心升级后能重连并恢复 UI，不能因 HTTP 503/404 导致错误写配置。
10. 安全设置应具备回归测试：恶意网页、未授权 localhost 客户端、端口替换、崩溃重启、过期 Token、并发操作、WebView 导航。

注：Android 的应用间隔离与 WebView 网络访问策略需要真机验证；不要默认本地 HTTP 端口仅本应用可见。

## 6. 平台差异与部署

### 6.1 Android

保留 Root 模块作为 Go Core 和 sing-box 的安装及运行载体：

```text
Magisk / KernelSU / APatch
        ├── netproxyctl (Go + Embedded WebUI + API)
        └── sing-box
                   ↑
       Tauri Android APK (Kotlin Plugin + WebView)
```

**Android 插件第一批能力**：模块/Root 状态、App 应用清单与图标、原生文件选取/分享、通知、快捷设置磁贴；旧 Compose 项目中相应 Kotlin 能力优先迁移而非重写。

**兼容要求**：保留既有 Android `applicationId=com.fanjv.netproxy`、签名密钥、递增的 versionCode；验证现有 APK 覆盖升级、用户数据与旧模块协议，不允许要求老用户默认卸载重装。新 Tauri Android 需生成完整可安装 APK，并确认 Android 8.0 基线。保留原 APK 直到新版本达到功能一致。

### 6.2 Windows

推荐：独立的 Go 后台/Windows Service（权限根据 TUN 需要设计），Tauri 为普通用户客户端；两者通过安全本地 IPC 或受鉴权的 loopback API 通信。

首期：Mixed HTTP/SOCKS 入站与节点/订阅/配置管理；后续再实现 TUN、管理员权限引导、DNS 路由回滚、服务安装和托盘等能力。

特别注意：Go 后台若以高权限服务运行，不能让系统其他用户通过共享 localhost 随意操作；Windows Named Pipe / ACL 或等效的用户鉴权策略需要单独设计。

### 6.3 Linux

推荐：无 UI 的 `netproxyctl` + `sing-box` 可作为 systemd service 部署；Tauri Linux 仅作为可选桌面客户端。

首期：Mixed HTTP/SOCKS；第二阶段 TUN、路由与 DNS；最终处理 systemd 集成、权限、网络变更事件、异常恢复、多用户使用与桌面通知。

Go Core 目录遵循 Linux 常用目录规范或 XDG，避免复用 Android 的 `/data/adb/`、`/dev/netproxy` 等硬编码路径。

## 7. Go Core 的跨平台改造清单

| 改造领域 | 主要源码 | 处理建议 |
| --- | --- | --- |
| 路径 | `internal/paths/paths.go` | 平台默认路径及覆盖配置；保留 Android 布局 |
| 进程管理 | `internal/service/control.go`、`internal/module/service_process_*` | Windows 原生进程身份检测；Linux /proc；进程优雅退出 |
| cgroup | `internal/module/cgroup.go` | Android 专属或显式能力检测；Windows 禁止调用 |
| 引导 | `internal/module/lifecycle.go` | 分离 Android `resetprop` 和通用启动业务 |
| Worker | `internal/worker/process_*`、`network_*` | 真正实现 Windows 进程管理；Linux 出口发现重做 |
| 入站 | `internal/inbound/` | 三端 Mixed/TUN 配置；Android eBPF 保持不变 |
| 应用标识 | `internal/inbound/applications.go` | Android package/UID 独立适配；桌面不复用 Android 语义 |
| 状态与日志 | `internal/service/control.go` | CPU/内存等指标由平台抽象提供 |
| Web 服务 | `internal/webserver/`（新增） | 内置 UI、管理 API、事件流、安全鉴权 |
| Web 静态资源 | `internal/uiassets/`（新增） | 编译打包 WebUI 产物 |
| HTTP/CLI 契约 | `cmd/netproxyctl/` | 共用业务层，独立协议版本 |
| 配置模板 | `src/module/config/` | 原 Android 模板不动，新增桌面模板 |

### 入站策略

| 入站/能力 | Android | Windows | Linux |
| --- | --- | --- | --- |
| Mixed HTTP/SOCKS | 可支持 | 首期必需 | 首期必需 |
| TUN | 保留现有 Root TUN | 后续适配 | 后续适配 |
| 当前 reF1nd eBPF | 保留 | 不支持直接复用 | 另行评估，不作为首期目标 |
| Android 包名 / UID 分应用 | 保留 | 不适用 | 不适用 |
| 桌面应用或进程分流 | 不套用桌面模型 | 单独设计 | 单独设计 |

Windows/Linux 的二进制都需要验证 reF1nd sing-box 当前版本是否支持预期编译目标，以及该分支 Service API、入站、热重载和控制功能是否可用。**只让 Go 交叉编译成功不等于移植完成**。

## 9. 分阶段实施与验收标准

### P0：验证最难的前提，先证明架构可行

工作：建立最小 Go 内置页面；Tauri Android/Windows/Linux 主 WebView 指向 Go loopback URL；通过受限插件调用一个无风险原生能力；验证 HTTP API 鉴权与失败页面。

**验收**：三端能加载 Go UI，能在安全边界内调用插件；未运行 Go Core 时不会白屏；未经授权的本地进程和任意网页不能执行高权限插件。

**阻断项**：如果 Tauri 远程页面的原生插件信任链不能可靠建立，先调整通信边界再进入 P1。

### P1：Go Core 内置 WebUI 与 HTTP 管理 API

工作：`go:embed`、API、事件流、会话验证、接口版本、原有 CLI 共用业务处理。

**验收**：不安装 Tauri，运行 Go Core 后即可用浏览器完整管理节点和订阅；通过 CLI 与 WebUI 操作时状态一致；代理服务不依赖 UI。

### P2：完整 React WebUI

工作：仪表盘、节点与订阅、规则、入站、JSON 编辑器、日志、更新进度、移动端响应式布局、主题和国际化。

**验收**：覆盖原 Android Compose 主流程；页面重载后状态来自 Go，而非缓存假数据；低性能 Android 真机能流畅使用。

### P3：Android 迁移与兼容

工作：Kotlin Tauri 插件复用现有 libsu、应用清单、通知和快捷磁贴；验证 APK 签名覆盖升级、module/core 协议兼容。

**验收**：旧版 Android 用户能够直接升级；关闭 App 后代理保持运行；Android 专属能力与旧版核心功能不退化。

### P4：Windows/Linux 核心移植

工作：路径、进程/Worker、网络出口、Mixed 配置、服务注册、安全 IPC、诊断日志。TUN 作为下一子阶段。

**验收**：可安装、启动、停止、导入订阅、节点切换、查看日志；异常退出后能恢复或明确报告；安装卸载无遗留服务。TUN 验收另列网络恢复与防回环测试。

### P5：发布工程与文档

工作：三端 GitHub Actions 构建、Android 签名、Windows 包与签名策略、Linux 包、版本矩阵、回归测试、迁移说明。

**验收**：开发包和正式发布包均可复现；安装与升级有回归测试；Go/UI/Tauri 版本不匹配时能安全提示；原模块发行流程不受影响。

> 顺序说明：P0 应优先于完整 React UI 重写。Android Kotlin 插件和桌面 Go 平台抽象可以平行推进，避免新 UI 完成后才发现关键 Tauri 信任边界不适用。

## 10. 面向功能的能力契约

推荐拆成两类能力，不要混用：

```ts
// Go Core 提供：真实业务能力与运行状态
interface CoreCapabilities {
  apiVersion: number;
  platform: 'android' | 'windows' | 'linux';
  supportedInbounds: Array<'mixed' | 'tun' | 'ebpf'>;
  canManageService: boolean;
  canManageSubscriptions: boolean;
  canReadLogs: boolean;
}

// Tauri 提供：操作系统图形化/交互能力
interface NativeCapabilities {
  platform: 'android' | 'windows' | 'linux' | 'browser';
  appEnumeration: boolean;
  quickSettingsTile: boolean;
  systemTray: boolean;
  notifications: boolean;
  nativeFilePicker: boolean;
}
```

UI 渲染由**能力检测**决定，而不是堆积大量 `if (Android)`、`if (Windows)`。

一个平台的原生插件缺失时，应能继续使用通用业务：例如浏览器管理时不可用的 QS Tile 入口隐藏，但节点管理仍然有效。

## 11. 发布模型与升级约束

### Android

- 模块包包含：Go Core、sing-box、内置 UI、所需配置和资源。
- APK 仅包含：Tauri 运行外壳、最小连接/错误页、Android 插件和必要资源。
- UI 变更由模块/Go Core 更新发布；原生插件变更由 APK 更新发布。
- 保持旧 Android 包名和证书，验证 versionCode 增长和旧版覆盖安装。
- 不依赖 Google Play 才能获取核心版本；需要时提供用户可控更新方式。

### Windows / Linux

- 安装包需要提供：Tauri App + 对应架构的 Go Core + sing-box + 默认配置模板。
- 安装器负责服务安装、权限/可执行路径、数据目录和卸载策略；客户端 UI 可以随应用安装包独立更新。
- Core 与 Tauri 版本不匹配时必须提供兼容错误和安全回退策略。
- 跨平台默认配置不能直接将 Android `module.json` / `inbound.json` 语义照搬过来。

### 重要现实约束

Tauri 本身不是 Go Core 的启动管理者；但在桌面系统首次安装时，可以由安装器负责服务注册，并由 Tauri 提供“检查服务/打开服务管理”的用户入口。Android 的 Root 模块继续持有真实启动职责。

## 12. 风险、缓解与禁止发布条件

| 风险 | 影响 | 建议措施 |
| --- | --- | --- |
| 将 localhost 误认为安全边界 | Root 管理 API 被本地 App 滥用 | 端到端鉴权、受限 Capability、测试端口劫持 |
| Tauri 远程页面无法安全调用原生插件 | 架构关键能力受阻 | P0 先进行 Android/Windows/Linux 端到端验证 |
| Android WebView 无法加载或存在性能问题 | Android 端体验倒退 | 真机覆盖测试、保留旧管理器作为回退 |
| Go Core 升级与 APK 脱节 | 功能调用失败 | `api_version` + `native_capabilities` 与版本握手 |
| Windows 服务高权限化 | 本地提权或跨用户误操作 | 每用户认证/ACL、最小权限、分离系统服务通道 |
| Windows TUN 清理失败 | 用户断网 | 异常退出回滚、DNS/路由恢复测试 |
| 将 Android 目录直接改造成桌面模板 | 老用户配置损坏 | 平台模板隔离，按字段进行迁移与兼容测试 |
| 旧 APK 签名或 package 不兼容 | 无法覆盖升级 | 保留原包名与签名证书，CI 安装升级验证 |
| 贸然移除 Compose | 功能退化 | 新旧并行、逐页迁移、达到验收标准再删除 |

**禁止进入正式发布的情况**：出现未鉴权的高权限管理接口、任何外部页面可直接调用 Root 插件、Android 旧版无法无损升级、基本关闭/重启会中断代理、Windows TUN 恢复流程未经测试。

## 14. 需要进一步确定的产品决策

| 决策 | 推荐方案 | 理由 |
| --- | --- | --- |
| Tauri 是否包含完整业务 UI | 否，仅包含连接/诊断页 | 只维护 Go 内置的一份业务 UI |
| Android 是否保留独立 Compose 项目 | 迁移期间保留 | 降低老用户升级风险 |
| 是否保留独立 KernelSU WebUI | 不必 | 同一 Go WebUI 已可通过浏览器访问 |
| 浏览器访问权限 | 默认仅本机 + 显式认证 | 不把 Root 管理能力暴露给局域网 |
| Windows/Linux 第一版入站 | Mixed | 降低系统路由和权限复杂度 |
| Android 核心运行 | Root 模块 | 不依赖 APK 后台保活 |
| Go API 是否代替 CLI | 不代替；两者共享业务 | 保留脚本自动化与调试兼容 |
| Windows/Linux 管理程序是否必须装 | 不必须 | 无 GUI 服务器环境仍可使用 |
| 是否现在重命名 repo 和目录 | 不立即进行 | 先验证可行性与兼容性 |

## 15. 成功标准

9.0 的成功不只是“三端都能打开窗口”，而是：

- 同一份 React WebUI 在浏览器和三端 Tauri 中显示一致的业务状态；
- Go Core 不依赖 Tauri，单独运行也能管理代理和提供界面；
- Kotlin/Rust 平台代码不复制 Go 的业务状态与配置处理；
- Android 用户能够顺利从旧管理器升级；
- Windows/Linux 能实际启动、管理和停止兼容 sing-box 进程；
- Core、UI、Tauri 可按合理的版本边界升级；
- 即使前端不可用，CLI 与代理服务仍可正常工作；
- 本机高权限管理 API 和 Tauri 插件无法被未授权调用。

**一句话总结：NetProxy 9.0 = 独立 Go 控制面 + 内嵌 React WebUI + 可选 Tauri 原生外壳 + 跨平台 sing-box 运行环境。**
